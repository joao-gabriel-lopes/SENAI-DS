O ponto essencial

01 · Fundamentos

O que é JWT?

JWT significa JSON Web Token, um padrão aberto definido pela RFC 7519 para representar informações em um formato compacto.

Uma credencial assinada

Após validar as credenciais do usuário, o servidor pode emitir um token com declarações (claims), como o identificador do usuário, permissões e horário de expiração. O cliente envia esse token nas próximas requisições.

Em resumo: o servidor emite; o cliente apresenta; a API valida o token antes de liberar o recurso.

Autenticação x autorização

Autenticação: verifica quem é o usuário.

Autorização: verifica o que esse usuário pode fazer.

Um JWT válido não significa acesso irrestrito: a API ainda deve verificar permissões e regras de negócio.

02 · Motivação

Quais problemas ele ajuda a resolver?

JWT pode simplificar a propagação de identidade entre serviços, especialmente em APIs distribuídas.

⇄

Compartilhar identidade

O cliente pode apresentar o mesmo token em chamadas a diferentes endpoints ou serviços que confiem no emissor e validem o token corretamente.

▤

Reduzir dependência de sessão

Tokens autocontidos podem evitar a necessidade de consultar uma sessão no servidor em toda requisição. Isso não elimina todo estado do sistema.

⌘

Integrar APIs e serviços

Um formato padronizado facilita a comunicação entre aplicações web, mobile, backends e microsserviços.

Atenção: JWT não criptografa automaticamente o conteúdo, não impede roubo de token e não resolve sozinho logout, revogação, autorização ou armazenamento seguro.
03 · Funcionamento

Como funciona na prática?

O servidor assina o token com uma chave. Ao recebê-lo, a API verifica a assinatura e os critérios de validade antes de confiar nas claims.

O processo em 4 passos

  1. O usuário envia credenciais para o endpoint de login usando HTTPS.
  2. O servidor valida as credenciais e cria claims necessárias.
  3. O servidor assina e devolve um token de acesso.
  4. O cliente envia o token nas requisições; a API valida assinatura, expiração, emissor e audiência, conforme configurado.

O que a assinatura garante?

Uma assinatura válida permite detectar se os dados assinados foram alterados e ajuda a verificar que o token foi produzido por quem possui a chave correspondente.

Ela não esconde os dados do payload. Qualquer pessoa que tenha um JWT comum pode decodificar seu conteúdo.

Regra prática: nunca inclua senhas, segredos ou dados pessoais desnecessários no payload.

05 · Estrutura

Quais são os componentes do JWT?

Um JWT assinado comum tem três partes codificadas em Base64URL, separadas por pontos.

1. Header{"alg":"HS256","typ":"JWT"}

Indica o tipo de token e o algoritmo usado para a assinatura.

2. Payload{"sub":"123","role":"user","exp":...}

Contém claims, ou declarações, sobre o sujeito e o contexto do token.

3. SignatureHMACSHA256(...)

Permite verificar a integridade e a origem do token conforme a chave e o algoritmo.

Formato ilustrativo de um JWT
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjMiLCJleHAiOjE5MDAwMDAwMDB9.assinatura_de_exemplo
Importante: o token acima é apenas ilustrativo, não é um JWT válido para autenticação. Base64URL é codificação, não criptografia. Em JWE (JWT criptografado), a estrutura é diferente.

Claims registradas

iss emissor, sub sujeito, aud audiência, exp expiração, iat emissão, nbf não válido antes.

Claims personalizadas

Podem representar dados úteis como organização ou escopo, desde que sejam mínimos e não sensíveis.

Algoritmos e chaves

Use bibliotecas confiáveis, permita apenas algoritmos esperados e proteja as chaves. Não aceite o algoritmo apenas porque o token o declara.

06 · Validade

Token e tempo de expiração

O claim exp informa quando o token deixa de ser válido. O tempo deve equilibrar usabilidade e impacto de um possível roubo.

Por que expirar?

  • Limita a janela de uso de um token roubado.
  • Reduz o período de validade de credenciais antigas.
  • Permite renovar o acesso com mecanismos controlados.

Exemplos de duração são decisões de projeto, não regras universais. Tokens de acesso costumam ter vida relativamente curta; refresh tokens devem ser tratados com proteção especial.

Simulador ilustrativo
00:15:00

Um token com essa duração deixa de ser aceito após o prazo, conforme a validação da API.

Este simulador explica a duração; ele não cria, valida nem expira um token real.

Access token

É enviado para acessar recursos protegidos. Mantenha sua validade limitada e restrinja permissões e audiência ao necessário.

Refresh token

É usado para obter novos access tokens sem exigir login a cada expiração. Deve ser armazenado com cuidado, ter rotação e detecção de reutilização quando aplicável, e possuir estratégia de revogação.

Logout e revogação: um JWT assinado normalmente continua criptograficamente válido até expirar. Para encerrar sessões antes disso, avalie refresh-token revocation, listas de bloqueio, versões de sessão ou tokens opacos, conforme os requisitos.
07 · Mão na massa

Exemplos de uso

Os trechos são didáticos. Adapte a biblioteca, as chaves e o armazenamento ao seu ambiente de produção.

1. Login — cliente pede o token

O cliente envia credenciais a um endpoint de login. A resposta pode conter um access token.

HTTP · POST /login
POST /api/login
Content-Type: application/json

{
  "email": "ana@exemplo.com",
  "password": "senha-digitada"
}
Nunca envie senhas em URL ou por HTTP sem TLS. O exemplo não deve ser usado para registrar ou imprimir senhas em logs.

2. Chamada protegida

O cliente apresenta o token no cabeçalho Authorization usando o esquema Bearer.

JavaScript · fetch
const response = await fetch("/api/perfil", {
  headers: {
    Authorization: `Bearer ${accessToken}`
  }
});

if (response.status === 401) {
  // Token ausente, inválido ou expirado
}

3. Criar token no servidor

Pseudocódigo: a biblioteca confiável cuida da codificação e assinatura.

Pseudocódigo
const accessToken = jwt.sign(
  { sub: user.id, role: user.role },
  secretKey,
  {
    expiresIn: "15m",
    issuer: "minha-api",
    audience: "minha-app"
  }
);

É um exemplo de estilo Node.js com uma API de biblioteca JWT comum; confirme a sintaxe da biblioteca escolhida. A chave deve vir de um gerenciador de segredos ou variável segura, nunca ser publicada no frontend.

4. Validar antes de autorizar

Não basta decodificar o token: valide assinatura e claims usando a configuração esperada.

Pseudocódigo
const claims = jwt.verify(token, secretKey, {
  algorithms: ["HS256"],
  issuer: "minha-api",
  audience: "minha-app"
});

// Depois, verifique permissões e regras
// antes de devolver o recurso protegido.

09 · Boas práticas
Checklist de segurança
JWT é parte de uma arquitetura de autenticação. A implementação segura depende de toda a jornada.

  

   
Faça
  • Use HTTPS em todas as etapas.
  • Valide assinatura, exp, iss, aud e nbf quando aplicável.
  • Defina algoritmos permitidos explicitamente.
  • Use tokens curtos e claims mínimas.
  • Proteja chaves e planeje sua rotação.
  • Implemente autorização no servidor.

   
Evite
  • Guardar senhas ou segredos no payload.
  • Confiar apenas em decodificar o token.
  • Armazenar tokens em locais acessíveis a scripts sem avaliar XSS.
  • Colocar tokens em URLs ou logs.
  • Usar o mesmo token indefinidamente.
  • Presumir que logout invalida automaticamente todo JWT emitido.

  

  
Armazenamento no navegador: a escolha entre cookies HttpOnly; Secure; SameSite e armazenamento acessível ao JavaScript depende da arquitetura. Cookies exigem defesa contra CSRF; tokens acessíveis a scripts aumentam o impacto de XSS. Avalie os riscos do seu cenário.

 


 

  
10 · Dúvidas comuns
Perguntas frequentes

  
JWT é criptografado?
Não necessariamente. Um JWT assinado (JWS) normalmente tem payload legível após decodificação. Para confidencialidade é necessário um formato criptografado, como JWE, ou outra proteção apropriada.

  
JWT substitui HTTPS?
Não. HTTPS protege o tráfego em trânsito. O token precisa ser transmitido por um canal seguro para reduzir o risco de interceptação.

  
Posso guardar qualquer informação no payload?
Não é recomendado. O payload de um JWT assinado comum não é secreto; inclua apenas claims necessárias e evite dados sensíveis.

  
O que acontece quando o token expira?
A API deve rejeitá-lo. O cliente pode pedir um novo access token por um fluxo de renovação seguro ou exigir novo login, dependendo da arquitetura.

  
JWT é sempre melhor que sessão?
Não. Sessões tradicionais podem ser mais simples quando o servidor precisa de revogação imediata e controle centralizado. A escolha depende dos requisitos, escala e modelo de ameaça.
